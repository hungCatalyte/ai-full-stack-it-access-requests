# Build plan from planning/spec.md

## Choices

- **Runtime:** proposed Python 3.11+ with standard-library SQLite, HTTP transport, and unittest, plus a pinned JSON Schema validator; this fits the existing Python starter and keeps the service footprint small.
- **Interface:** proposed CLI via `python3 -m access_requests`, with intake, queue, pending, history, retry, resume, export, and accuracy actions; a second terminal can inspect shared state while intake runs.
- **Test command:** `env -u API_KEY python3 -m unittest discover -s tests -v`; tests block network access, inject fake credentials only into local configuration/transport assertions, and use temporary directories and deterministic synchronization.
- **Model call:** proposed OpenAI Responses API over an injected HTTP transport, with `API_KEY` read only in live mode and a configurable model ID; offline fixtures supply complete/refusal/incomplete/error envelopes and all build checks use mock mode. Provider/model selection is awaiting the user answer; there is no live call in this plan.

This is a plan only: all modules, fixtures, commands, and artifacts named below are future work. No application code, tests, fixture files, commits, or external submissions are created by this step. These choices are implementation proposals rather than added spec requirements.

Architecture proposal: `access_requests/` holds ingestion, extraction/provider adapter, validation, policy, repository, worker, CLI, and accuracy modules; `tests/` holds unittest cases and future `tests/mock_responses/` fixtures. A SQLite database is the authoritative store for current records, source revisions, history, and pending work. Current deliverables are exports, and history is retained separately. Support is initially proposed for overlapping processes on one host and local disk, not a multi-host database guarantee. Bounded concurrency and timeout values are configurable operating limits rather than invented throughput promises.

Documentation consulted: [Python SQLite](https://docs.python.org/3.11/library/sqlite3.html), [unittest](https://docs.python.org/3.11/library/unittest.html), and the [Responses request/response reference](https://developers.openai.com/api/reference/resources/responses/methods/create). The latter defines completion and refusal response representations; model availability and the supported model ID must be checked when selecting the configuration.

Unclear behavior to ask the person before implementation (the corresponding questions in the spec remain unchanged):

- **Q-02 / R-01, R-101, R-136:** which provider/model should be supported? An OpenAI Responses adapter is proposed; supported-model selection and provider-specific envelopes are conditional on the answer.
- **Q-34 / R-88, R-96, R-115:** should normal unchanged reruns reuse failures or automatically retry them, and should explicit retry permit refreshing a prior success? The plan requires a way to exercise success followed by failed retry but does not silently define ordinary-rerun behavior for errors.
- **Q-35–Q-36 / R-07, R-10, R-12:** which admitted source revision should win when different versions overlap? User clarification has been requested; test same-source overlap now and leave the different-source winner assertion pending.
- **Q-09–Q-10, Q-13, Q-18–Q-19, Q-23 / R-20, R-28, R-38–R-49, R-62:** supplied examples ground the cases below, but blank facts, mixed intentions, correction vocabulary, and subtle override detection have no exhaustive source rule; keep unprovided edge cases explicit rather than inventing acceptance outcomes.
- **Q-25–Q-26 / R-66–R-69:** the ordinary withdrawal case follows the stated ordered rules; obtain clarification before adding special conflict/withdrawal exceptions or modifying another document.
- **Q-29, Q-33, Q-37–Q-40, Q-43, Q-46, Q-49–Q-50:** outer metadata encoding, provenance fingerprints, attempt IDs, same-host scope, retry budgets, history layout, request-evidence shape, and scoring are documented implementation proposals to review, not policy additions. Proposed scoring is stated in the test plan; no passing accuracy threshold is invented.
- **Q-57–Q-59 / R-133–R-135:** facilitator capture acceptance and Classroom instructions remain external release dependencies.

Per the [plan-from-spec skill](../.agents/skills/plan-from-spec/SKILL.md): “Where a spec line is unclear, say so in the plan and ask the person; do not guess a rule.” The plan can be reviewed now; dependent implementation decisions remain open.
